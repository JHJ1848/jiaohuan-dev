# 工程原则与核心准则

术语：工作流(Workflow)负责路由与交接；开发(Dev)、诊断(Debug)、缺陷修复(Bugfix)是执行链；探索(Explore)是只读澄清；意图推测(Intent Inference)是还原历史演进初衷、架构断层与演进盲区的固定分析节点；价值评估(Value Assessment)决定是否归档；场景(Scene)是可复用问题上下文；陷阱(Gotcha)是场景内可复用误判；循环(Loop)是按证据回查；智能体(Agent)是执行者；状态机(State Machine)不是本流程控制面。

---

## 核心架构准则 (冲突裁决依据)

1. **约束优先于便利**：业务约束、工程安全与白名单隔离永远优先于临时快捷实现。
2. **原始证据优先于推测**：记忆与文档只能记录已确认事实与断言，严禁将假设、推测或未验证结论写成既成事实。
3. **主记忆唯一权威**：`docs/MEMORY.md` 是全项目唯一主记忆枢纽；根目录 `MEMORY.md` 仅为向下兼容垫片。
4. **历史兼容与不变量守护**：新逻辑必须兼容已确认的历史约束与业务初衷，严禁破坏历史业务不变量；排查复杂历史逻辑时强制执行意图推测节点。
5. **最小可逆改动**：只改动目标必要范围内的代码，严禁顺带重构、无关格式化或吞没异常；新改动与旧逻辑冲突时优先寻求兼容解。
6. **文档与代码分离**：API 契约归入 `docs/api/`，业务记忆归入 `docs/memory/`，单次改动归入 `docs/change/`，临时草稿归入受管临时目录，严禁跨层混杂。

---

## 文档与术语规范

- 主分支的 Skill 与参考文档使用极简中文；首次出现的通用专业术语使用“中文(English)”形式，命令、路径、字段和值保持机器兼容。英文版本在独立分支维护。
- 优先使用已有行业通行术语，严禁发明同义新词；新增术语必须有明确必要性、单一定义与使用边界。
- Skill 文档只保留触发条件、执行步骤、输入输出、停止条件、兼容边界与必要命令示例，公共原则统一引用本文档，严禁在 Skill 中大篇幅复制。
- **简洁写入**：文档只写客观事实、必要字段和验证结果。避免套话、空话、重复背景和无实际作用的修饰语；先说问题、原因和结果，再补充必要边界。

---

## 目标与证据取证

- 以用户目标和可核验证据驱动：先取得足以决定下一步的最小事实，再做最小、可回退动作。
- 用第一性原理排除非关键因素：先证明现象的入口、输入、状态与因果链，再讨论外部依赖或隐藏条件。
- 自动路由不等于修改授权。业务含义、影响范围、高风险写入或计划不明时，先探索(Explore)或确认；不得重复询问已确认事项。
- 未进断点、无日志或结果未变化时，先证明入口、部署版本、输入、调用链和状态是否到达；不得先归因外部库、框架或单一猜测。
- 结论严格区分为：已证实、已排除、待确认、已实施。推测历史意图可指导取证，不能写成事实；不得保存模型原始思维链。

## 历史意图推测与最小改动

- 修改前或排查复杂链路时，必须执行【意图推测(Intent Inference)】：按时间轴查 Git（如 `git log -L`、`git log -p`、`git blame`）、`docs/change/`、记忆、接口契约与数据状态，还原代码最初为何这样写、经历了哪些演进阶段。
- 意图推测重点排查演进断层：区分复用初衷、审计不变量（如原值防篡改/副本隔离）与历史过渡残留（如统配覆盖）；重点识别“状态继承短路”（上游暂态穿透下游计算）与“过渡逻辑残留”（历史统配二次篡改显式赋值）。
- 严禁粗暴覆盖历史逻辑；必须在保护历史业务不变量的前提下给出全局兼容的手术式方案，方案需用户明确确认。
- `.agents/AGENTS.md` 是约束，`docs/MEMORY.md` 是事实与索引；两者的规则、目标或范围冲突时停止并请用户裁决，不得以记忆覆盖项目约束。
- 一次只验证一个原因或改动，控制因变量；先使主链路可运行、日志可读，再处理业务优化或隐藏条件。
- 只实施确认范围内的最小、可逆改动：不顺手重构、不批量格式化、不加未经证实的兜底、默认值、吞错或冗余保护。
- 日志只记录决定路径的输入、状态和结果，格式优先为 `[模块功能] 内容`；严禁记录令牌、密码、Cookie 或个人敏感信息。

---

## 验证与交付

- 简单改动做严格目标核对；复杂、跨边界或高风险改动明确交由用户实测。真实接口、数据库或生产相邻环境只在用户明确授权后访问。
- 接口验证使用最小请求和精确断言，写入与读取分开执行。令牌仅从环境变量读取；登录凭据仅在用户明确授权的当次进程使用，绝不写入脚本、文档、记忆或响应。
- 出现计划外疑点、业务歧义、验证失败或风险扩大时停止修改，回到探索(Explore)或诊断(Debug)重建计划。
- 结束前按影响面检查遗漏、兼容性、维护性、性能、日志追踪和回退条件；不为假设风险预先堆叠功能。
- 有代码、配置、脚本或迁移等可审查实施变更时，`memory-put` 前必须进入 `code-review`；仅文档整理或未产生实施变更时不强制进入。
- 审查发现阻断、重要或未证实风险时不得归档：已证实的修复回到 `dev`，根因、历史冲突或未知项回到 `bugfix`；修复后重新审查。没有可用的独立审查能力时必须报告“未执行”并交用户决定，不得静默放行。

## 记忆与文档体系 (三层记忆架构与 API 分离)

- **第一层（主记忆与工程约束）**：
  - `.agents/AGENTS.md`：约束工程代码环境、任务识别规则（Plugin 自身能力 vs 被集成业务项目）与操作规范；
  - `docs/MEMORY.md`：沉淀核心架构准则、全局底层业务不变量、专题索引与全局变更索引，为全项目唯一受控主记忆枢纽；根目录 `MEMORY.md` 仅为兼容垫片。
- **第二层（专题受控记忆与 API 契约）**：
  - `docs/memory/<专题>.md`：与 `docs/change/<专题>/` 保持 1:1 强绑定。仅维护长期架构事实、业务契约、物理白名单与该专题的变更索引摘要（格式：`标题 + 日期 + 一句话摘要 + 相对路径`，摘要控制在 1-2 句以内），严禁堆砌单次改动流水账；
  - `docs/api/README.md` 与 `docs/api/<模块>.md`：接口契约规范目录。与业务记忆物理分离，只记录接口字段、状态码、权限与请求样例，不承载业务取舍和变更原因；禁止记录真实凭据与长 ID。
- **第三层（专题变更明细）**：
  - 所有具体工程实施与排障改动必须写入对应专题目录 `docs/change/<专题>/YYYY-MM-DD_中文简述.md`；
  - **新记录统一采用四段式结构**：
    1. **一、问题/需求**：只写现象、目标和范围，控制在几句话内；
    2. **二、原因分析**：只写已确认原因、关键证据和排除结论；没有证据的标记为“待确认”，严禁将推测写成事实；
    3. **三、测试结果**：记录验证方式和结果；如果尚未测试，明确写“未测试”或“待用户验证”；
    4. **四、备注**：记录风险、TODO、回退方式、关联专题、API 契约、替代记录或其他补充信息。
  - **新记录安全与质量红线**：
    * 严禁复制完整代码片段；
    * 严禁复制完整接口响应或完整运行日志；
    * 严禁记录易失效的具体代码行号；
    * 严禁写长篇项目背景与无关客套；
    * 严禁整段粘贴用户原始对话或模型思维链；
    * 避免套话、空话和无实际作用的修饰语，文字保持简短，重点清楚。
- **历史记录向下兼容**：
  - 对历史平铺记录（`docs/change/*.md`）、既有五段式及六段式场景记录保持只读结构兼容与检索解析；
  - 未经用户明确授权，严禁对历史 change 文件进行批量重写、重命名或物理迁移。
- **临时材料管理**：
  - 临时证据存放于 `.agents/project-memory/temp/<task>/`；异步子智能体(Agent)只写草稿，主任务唯一维护 `path.json` 并执行正式归档。
- **交付输出**：
  - 任务交付时，必须说明实际证据、未知项、改动、验证边界，并列出实际引用的记忆文档；未引用时写“无”。
