# 工程原则

术语：工作流(Workflow)负责路由与交接；开发(Dev)、诊断(Debug)、缺陷修复(Bugfix)是执行链；场景(Scene)是可复用问题上下文；陷阱(Gotcha)是场景内可复用误判；循环(Loop)是按证据回查；智能体(Agent)是执行者；价值评估(Value Assessment)决定是否归档；状态机(State Machine)不是本流程控制面；探索(Explore)是只读澄清。

## 文档与术语

- 主分支的 Skill 与参考文档使用简洁中文；首次出现的通用专业术语使用“中文(English)”形式，命令、路径、字段和值保持机器兼容。英文版本只在独立分支维护。
- 优先使用已有行业术语，不发明同义新词；新增术语必须有必要性、单一定义和使用边界。

## 目标与证据

- 以用户目标和可核验证据驱动：先取得足以决定下一步的最小事实，再做最小、可回退动作。
- 用第一性原理排除非关键因素：先证明现象的入口、输入、状态与因果链，再讨论外部依赖或隐藏条件。
- 自动路由不等于修改授权。业务含义、影响范围、高风险写入或计划不明时，先探索(Explore)或确认；不得重复询问已确认事项。
- 未进断点、无日志或结果未变化时，先证明入口、部署版本、输入、调用链和状态是否到达；不得先归因外部库、框架或单一猜测。
- 结论分为已证实、已排除、待确认和已实施。推测历史意图可指导取证，不能写成事实；不得保存模型原始思维链。

## 历史与最小改动

- 修改前按需查 Git、`docs/change/`、记忆、接口契约、入口、替代路径和数据状态；可疑注释、删除、绕过或停止调用先还原历史意图。
- `AGENTS.md` 是约束，`MEMORY.md` 是事实与索引；两者的规则、目标或范围冲突时停止并请用户裁决，不得以记忆覆盖项目约束。
- 一次只验证一个原因或改动，控制因变量；先使主链路可运行、日志可读，再处理业务优化或隐藏条件。
- 只实施确认范围内的最小、可逆改动：不顺手重构、不批量格式化、不加未经证实的兜底、默认值、吞错或冗余保护。
- 发布前无法完整验证的敏感改动，可在用户确认后保留旧实现注释并以清晰后缀的新方法或变量做临时对照；写明原因、回退方式和清理条件，不以此长期保留双实现。
- 日志只记录决定路径的输入、状态和结果，格式优先为 `[模块功能] 内容`；不得记录令牌、密码、Cookie 或个人敏感信息。

## 验证与交付

- 简单改动做严格目标核对；复杂、跨边界或高风险改动明确交由用户实测。真实接口、数据库或生产相邻环境只在用户明确授权后访问。
- 接口验证使用最小请求和精确断言，写入与读取分开执行。令牌仅从环境变量读取；登录凭据仅在用户明确授权的当次进程使用，绝不写入脚本、文档、记忆或响应。
- 出现计划外疑点、业务歧义、验证失败或风险扩大时停止修改，回到探索(Explore)或诊断(Debug)重建计划。
- 结束前按影响面检查遗漏、兼容性、维护性、性能、日志追踪和回退条件；不为假设风险预先堆叠功能。
- 有代码、配置、脚本或迁移等可审查实施变更时，`memory-put` 前必须进入 `code-review`；仅文档整理或未产生实施变更时不强制进入。审查固定本次变更的比较基点与范围，分别检查规格(Spec)和规范(Standards)，并按改动入口/模块用 `memory-get` 最小检索历史场景(Scene)、陷阱(Gotcha)、`docs/change/` 与 Git 约束；无统一 issue tracker 时以用户确认需求和实施计划作为 Spec，无 Spec 只跳过该轴并记录。
- 代码审查的 smell baseline 只作非阻断判断，不能借机扩大范围；审查只读检查并报告测试缺口，遵从项目默认不自动写/跑测试，测试缺口本身不阻断，除非用户另行授权。
- 审查发现阻断、重要或未证实风险时不得归档：已证实的修复回到 `dev`，根因、历史冲突或未知项回到 `debug`；修复后重新审查。没有可用的独立审查能力时必须报告“未执行”并交用户决定，不得静默放行。
- 交付说明实际证据、未知项、改动、验证边界和实际引用的记忆文档；未引用时写“无”。
