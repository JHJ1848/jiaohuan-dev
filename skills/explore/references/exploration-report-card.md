# 探索报告卡模板 (Exploration Report Card)

在完成系统现状只读探索、黑盒依赖摸底与调用链梳理后，必须严格按照本通用模板输出结构化报告卡，保持待命状态并向用户/主会话申请方案确认。

---

## 报告卡结构规范

```markdown
# [探索报告卡] <调研主题简述>

## 1. 调研背景与核心目标 (Context & Goal)
* **调研主题**：<如：多维数据筛选与流式导出前置调研 / 认证授权改造黑盒依赖摸底>
* **所属模块/工程**：<如：数据中心子系统 / 核心接入服务 / 客户端交互模块>
* **调研模型**：<分层定位模型 / 黑盒依赖摸底策略 / 初设比对 Gap Analysis / 异构存储核验 / 端协同追踪>
* **核心排查目标**：<明确需要探明的 1~3 个核心技术疑问、依赖边界或决策项>

---

## 2. 分层调用链现状 (Current State)
梳理既有架构各层的职责、组件与流转状态（采用“组件/文件名 + 核心函数/标签”精确定位，严禁使用易失效的绝对行号）：

| 架构层级 | 组件/模块 (相对路径) | 核心函数/接口/标签 | 当前职责与行为现状 |
|---|---|---|---|
| **接入与交互层** | `<如 API 路由 / 控制器 / 事件订阅器>` | `<接口端点或事件分发方法>` | 接收请求/事件，参数绑定与校验，调度业务层 |
| **业务与领域逻辑层** | `<如 领域服务 / 业务管理器 / 状态机>` | `<业务处理与流转方法>` | 组合多条件查询/业务编排，管理分页/流式处理 |
| **持久化与存储层** | `<如 数据访问组件 / ORM 映射 / 查询构造器>` | `<持久化方法或手写查询节点>` | 底层查询执行，检查动态条件拼装与软删除过滤 |
| **契约数据对象** | `<如 DTO / VO / 事件载荷定义>` | `<字段声明与校验注解>` | 现有契约支持的属性维度与缺失维度 |
| **存储底表与引擎** | `<主业务数据库 / 空间或多模存储底表>` | `<物理表名 / Collection / 视图>` | 底层持久化结构、物理列定义、字典编码映射与索引状况 |

---

## 3. 黑盒依赖与边界摸底 (Black-Box Dependency & Boundary)
* **工程源码 vs 宿主/三方组件/外部 SDK 边界**：
  * 工程本地可控源码：`<列出本地模块中可安全修改的源码组件>`
  * 宿主平台/依赖组件/外部 SDK：`<明确指出属于外部闭源 SDK、引擎基类或三方依赖包的组件，标注不可直接修改>`
* **继承覆盖与扩展机制**：`<是否存在基类重写、依赖注入覆盖、插件扩展点或事件拦截器>`
* **安全加解密与控制流**：`<传输层/持久化加密形态、权限拦截校验时机、是否有豁免放行策略>`

---

## 4. 差距与风险分析 (Gap & Risk Analysis)
* **入参与契约支持度差距**：`<对比需求维度与既有契约对象，明确哪些维度已支撑，哪些缺失>`
* **数据流转与性能/反压风险**：`<如全量打包 vs 分批流式拉取，大对象载入内存溢出风险>`
* **异构存储与数据方言风险**：`<跨存储方言函数差异、大小写敏感度、元数据系统视图查询差异>`
* **初设要求 vs 现状实现差距**：`<明确定性属于“源头设计缺失（底层未设计对应存储结构）”还是“代码逻辑缺陷（底层具备但链路未暴露）”>`
* **软删除与数据孤岛隐患**：`<手写复杂查询中是否遗漏逻辑软删除与有效性过滤条件>`

---

## 5. 架构一致性扩展建议 (Proposed Changes & Minimal Plan)
给出保持全局架构一致性的最小微创改动建议：
1. **契约对象扩展**：`<复用既有契约 DTO，仅最小化增补必要属性维度>`
2. **业务逻辑层调整**：`<参数透传至持久化层，补充流式反压或轻量化分批流转机制>`
3. **持久化与查询扩展**：`<补充动态过滤条件，确保跨存储方言兼容，显式补齐软删除过滤与排序确定性保证>`
4. **端协同交互建议**：`<输出给表现层的协同契约建议，如出参状态下发、控件禁用门限或字段命名映射>`

---

## 6. 待命确认门 (Waiting for Confirmation Checkpoint)
> [!IMPORTANT]
> **[探索阶段只读状态声明]**
> 本次调研全程遵循只读原则，未对任何代码、配置、数据库或静态资产执行修改。
> 
> **待对齐决策项**：
> 1. <决策点 1：技术方案选型（如数据流转采纳方案 A 还是方案 B）>
> 2. <决策点 2：初设验收口径确认（按收敛边界处理还是按扩展改动处理）>
> 3. <决策点 3：物理白名单范围与实施授权确认>
>
> 状态：**已进入待命状态 (Waiting for Confirmation)**，等待主会话/用户明确确认后，方可由主工作流分流至 `dev` / `bugfix` 实施。
```
