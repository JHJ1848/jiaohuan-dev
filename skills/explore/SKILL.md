# 探索 (Explore)

遵循 `rules/engineering-principles.md`。**全程只读，严禁擅自修改任何业务代码、配置文件、静态资产或存储底表。**

## 核心原则
1. **只读铁律**：探索阶段严禁任何写操作；一切行动聚焦于“现状调研、黑盒依赖摸底、事实取证与逻辑推演”。
2. **黑盒与依赖边界摸底优先**：改造前先穿透排查工程源码 vs 宿主/三方组件/外部 SDK 边界，防范类污染与盲目重构。
3. **真实客观证据链第一**：以真实协议 Payload、调用链拓扑、版本演进历史及存储底表状态为准，严禁盲信推测。
4. **待命确认门 (Confirmation Gate)**：输出《探索报告卡》后自动挂起待命，未经用户/主会话明确授权严禁进入实施。
5. **简洁记录**：探索报告只写现状、证据、未知项和下一步；避免套话、空话和重复背景。

## 触发条件
- 任务目标模糊、初设与实际现状存疑、复杂功能扩展前置调研、认证安全改造摸底、调用链或异构存储兼容性不清。

## 执行步骤
1. **上下文与记忆检视**：调用 `memory-get` 检索相关主记忆、专题记忆与历史变更记录，明确既有架构约束。
2. **多维依赖与黑盒摸底**：核查模块物理归属、源码与外部组件边界、基类继承覆盖机制与安全拦截链。
3. **全链路只读追踪**：穿透 `<表现端控制流/Payload → 接入与交互层 → 业务与领域逻辑层 → 持久化与存储层 → 存储底表>`。
4. **差距与风险分析 (Gap Analysis)**：比对初设期望与现状实现，甄别“源头设计缺失”与“代码逻辑缺陷”，核查存储方言兼容与软删除。
5. **产出《探索报告卡》并待命**：按模板生成标准报告卡（分层现状、依赖边界、差距分析、微创建议），进入待命状态向用户申请确认。

## 典型调研场景矩阵
- **多维全链路分层定位模型（功能扩展/流转筛选）**：层级组件定位、多维入参支持度、数据流转形态（打包/流式/分页）剖析、一致性扩展建议、待命确认门。
- **黑盒依赖摸底与安全控制流前置调研**：源码 vs 外部 SDK/组件依赖边界、数据加解密流向、身份权限校验流程、统一校验设施与规范。
- **初设/需求与现状比对（Gap Analysis）**：初设要求与标红未实现对比、模块物理归属、底层持久化 Schema 穿透核验、边界收敛建议。
- **异构存储与数据方言核查**：主业务数据库 vs 空间/多模存储方言函数、系统元数据字典大小写敏感、存储计算资源释放与软删除补齐。
- **端协同（表现端与运行时）全链路只读追踪**：表现层交互条件反推、请求 Payload 提取、接入层参数透传、底层查询与数据源头清洗。

详细实战步骤与排查技巧参见实战手册：[exploration-playbook.md](references/exploration-playbook.md)。

## 输入与输出
- **输入**：扩展需求、验收测试缺陷单、初始疑问、待探索业务模块或异常现象。
- **输出**：分层调用链现状、依赖边界摸底结果、差距分析、微创建议与标准 [探索报告卡](references/exploration-report-card.md)。

## 停止条件与交接规范
- 探索完成后严禁擅自升级为代码修改或写操作；
- 必须出具《探索报告卡》并保持待命；待用户/主会话确认架构决策、边界与授权后，方可路由至 `dev`（立项开发）或 `debug`（排障）。
