# 业务实施与工程验证要点手册 (Implementation & Verification)

本文档定义跨技术栈通用的软件实施核心工程规范、架构前置审视模型、数据防护准则与验收门禁。适用于 Web、移动端 App、Windows 桌面客户端、游戏运行时及后台服务等多种开发场景。实施过程中严格遵守 Allowlist 物理白名单，推行外科手术式精准实施。

---

## 规范一：新增功能前置五维审视

新增功能、模块扩展或跨层通信接入时，严禁未思考直接编码。必须结合既有工程事实完成五维审视：

1. **规范契约 (Specification Contract)**
   - 检查目标模块既有的分层架构、命名风格、异常与错误传播策略、并发/线程模型、事务传播、生命周期控制、日志标准与协议契约；
   - 确保新增实现与目标运行环境及当前模块的设计范式自然契合。

2. **实现链路 (Execution Chain)**
   - 从表现层/请求入口、安全准入门禁、参数有效性校验、核心业务计算、外部交互/底层状态存储到最终结果呈现，梳理端到端调用拓扑；
   - 显式标出主链路业务不变量、关键决策分支与失败降级出口。

3. **意图推测与历史契约 (Intent Inference)**
   - 时间轴 Git 考古：使用 `git log -L`、`git log -p` 与 `git blame` 还原目标上下文代码的最初设计背景与演进脉络；
   - 排查三大演进断层：状态继承短路、过渡规则残留二次篡改、审计事实与原值污染，确保新设计全局兼容历史业务不变量。

4. **复用机会 (Reusability Assessment)**
   - 检索同领域组件及相邻模块中现存的候选函数、工具类、常量与枚举；
   - 优先复用经过验证的现有模式，严禁复制同义实现；若候选方案不适用，需明确记录技术局限与差异原因。

5. **最小影响面 (Minimal Blast Radius)**
   - 比较“复用既有模块”、“扩展现有方法/类”与“新建独立实现”三种边界，选择改动代码文件最少、调用方改动最小且具备可逆回退能力的方案；
   - 严密评估对上下游调用方、数据持久层、协议契约与性能/内存开销的潜在影响。

## 规范二：外科手术式修改 (Surgical Changes)

1. **精准微创**
   - 每一行代码修改都必须能够直接回溯到当次任务目标；
   - 严禁借当次修改之机顺带进行无关代码重构、变量无意义重命名或全局格式化。

2. **清理自创冗余**
   - 严格清理因本次修改而失效的模块引用（import）、局部变量、私有辅助函数或多余参数。

3. **保护无关既有代码**
   - 严禁擅自删除或篡改他人编写的无关注释、待办项（TODO）或暂时未调用的代码；
   - 遵循现有错误处理契约，严禁静默吞没异常或破坏既有防御。

## 规范三：代码可读性、注释完备性与结构治理

1. **核心逻辑解释性注释 (`//`)**
   - 在复杂计算分支、状态机跳转、临界区同步、算法边界防御及兼容历史逻辑处，必须编写 `//` 注释，重点解释“为什么这么做（Rationale）”而非复述代码语法。

2. **核心方法契约注释 (`/** */`)**
   - 所有新增或核心公共接口/服务方法必须编写结构化 Docstring / Javadoc；
   - 清晰声明方法职责、各个参数的业务语义与有效范围、返回值特征及可能抛出的异常/错误码。

3. **方法规模与职责限制**
   - 单个函数/方法常规控制在 **50 ~ 200 行** 之间；严禁通过无意义空行凑下限；
   - 当单个方法超过 200 行或承担多重业务职责时，必须梳理原子封装边界与业务不变量，经确认后再行合理拆分。

4. **魔法值与枚举治理**
   - 严禁将数字阈值、业务状态码、事件标识、协议字符串作为字面量（Magic Value）散落在业务分支中；
   - 必须统一定义在对应领域的枚举类（Enum）或公共常量集中；外部协议字段集中在边界适配层做转换并附带来源注释。

## 规范四：数据防击穿、防覆盖与原子性防御设计

1. **有界核心数值资源的零负数原子守卫**
   - 涉及库存、资产、钱包余额、游戏生命值(HP)、体力(Stamina)、虚拟货币等有界核心数值资源时，严禁使用“先在内存查询校验 -> 再在内存相减 -> 最后直接写回存储”的非安全模式；
   - 必须在底层数据存储引擎或原子事务更新中施加原子扣减与正值守卫条件（如 CAS、条件原子写 `WHERE resource >= :deduct`）；
   - 严格依据底层原子操作的受影响行数或返回结果判定扣减成败，彻底杜绝并发穿透与数值倒贴负数。

2. **审计事实与关键流水的快照不可变性 (Write-Once Invariant)**
   - 账单结算快照、审批历史记录、关键交易归档、游戏结算记录等审计事实，严格遵循 **Write-Once（一次写入，永不覆写）** 语义；
   - 当业务发生重算、调整或驳回重做时，必须生成全新流水版本号或版本审计链，严禁在原主键或历史快照实体上就地覆盖更新。

3. **非托管/原生数据查询中的软删除与生命周期标记显式防御**
   - 在原生手写查询（如 MyBatis XML、手写 SQL、原生数据访问层或非 ORM 托管数据操作）中，凡涉及带有逻辑删除（`deleted` / `is_deleted`）或状态过滤的实体，必须显式补齐过滤条件；
   - 严禁盲目依赖可能由于未走框架层而漏配的全局切面或隐式拦截。

## 规范五：结构化日志链建设

1. **标准日志格式**
   - 关键路径日志格式统一采用：`[模块功能] 具体操作、状态与核心业务标识`；
   - 示例：`log.info("[订单结算] 开始执行资产原子扣减, bizId={}, deductAmount={}", bizId, amount);`

2. **日志拓扑节点布设**
   - **请求/事件入口**：记录输入参数摘要与上下文唯一跟踪标识（如 traceId、业务主键）；
   - **关键分支**：记录业务决策走向与非常规降级分支；
   - **外部交互与存储操作**：记录跨系统调用、底层写入前后耗时与状态结果；
   - **异常出口**：必须记录完整上下文特征与错误堆栈，严禁输出无意义或空的错误捕获日志。

3. **安全与合规红线**
   - 严禁在日志中输出明文密码、认证 Token、支付密钥、未脱敏敏感隐私数据；
   - 避免在密集循环体中大量输出完整报文，防范 I/O 阻塞与日志暴涨。

## 规范六：“构建/编译通过 != 需求落地”与交付验收

代码通过编译、打包或静态检查仅代表语法契约成立，绝不等于业务需求已正确落地。必须经过严密的证据化交付与独立审查。

1. **本地自测证据标准**
   - 计算与后端逻辑：核心业务逻辑单元测试必须通过，测试命令执行结果退出码必须为 0（Exit Code 0）；
   - 交互界面与表现层：完成前端/客户端代码构建自测，并提供可操作的刷新与人工核验要点。

2. **出具【用户测试要点指引卡】**
   - 涉及需要用户在界面、联调工具、调试器或测试环境中核验的场景，必须向用户出具结构化指引卡：
     ```markdown
     ### 📋 用户测试要点指引卡
     - **功能模块**：<对应业务功能模块与组件名称>
     - **前置准备**：<测试账号角色、客户端版本、前置数据环境与配置状态>
     - **操作步骤**：
       1. <步骤一：进入目标页面/触发何种事件/输入测试指令>
       2. <步骤二：提交何种参数/执行特定动作>
     - **预期结果与断言点**：
       * <界面呈现预期、状态流转断言、数据持久化字段核验>
     - **异常与边界验证**：
       * <输入边界值、弱网、并发或非法参数时的防御拦截表现>
     ```

3. **交付指引与归档材料极简精炼硬约束 (反假大空红线)**
   - 所有交付指引卡、代码注释与后续归档总结，必须使用精炼简洁的话语精准记录，严禁长篇大论和泛泛而谈，严禁说空话和废话；
   - 避免套话、空话、重复背景和无实际作用的修饰语；
   - 围绕客观事实、必要字段和验证结果展开。

4. **收尾强制审查门禁**
   - 实施变更完成后，必须强制流转 `code-review` 技能进行独立规范与回归审查；
   - 审查通过后，方可调用 `memory-put` 申请向 `docs/change/<专题>/` 归档。
