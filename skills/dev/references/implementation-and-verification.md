# 实施与验证要点

## 实施前

1. 复核确认计划、Git/change 历史、目标入口、业务不变量、影响面、回退条件和验收事实。
2. 计划外疑点、冲突历史逻辑、异常数据范围或未确认风险出现时立即停止；回到 `debug` 或探索(Explore)，不要边改边猜。

## 最小且可逆

- 保持既有风格、校验、事务、读写时序与兼容约定。每一行改动都能回溯到用户目标。
- 不替换整段实现、不重命名无关变量、不批量格式化；只清理本次产生的无用代码。
- 不为假设场景增加空集合返回、默认值、`try-catch` 吞错或多路径兼容。确需防护时先说明触发条件、证据和影响。
- 无法在发布前完整验证的危险改动，只有用户确认后才可采用“保留旧代码注释 + 具名临时新实现”对照；注明原因、回退点和后续清理条件。

## 循环(Loop)与日志

- 每次只改变一个已证实原因，先保证主链路无非业务错误、关键日志可见，再验证业务结果。
- 日志按 `[模块功能] 内容` 记录关键输入、状态、分支和结果；不打印秘密、完整身份证明或大对象。
- 合理反向推理隐藏前置条件，例如输入侧坐标系、权限、缓存、部署版本或配置覆盖；先取证再编码。

## 验证与收尾

- 默认不新建测试框架或自动回归。已获用户授权时，用最小命令、最小请求对或用户指定的人工验收验证；写请求与读请求分开，断言精确目标字段。
- Bash HTTP 工具使用 `--secret-header 'Authorization=API_TOKEN'`；令牌由环境变量提供。若用户明确授权登录接口与凭据，仅在当次进程换取令牌，不落盘。
- 验证失败或出现新行为，回到 `debug`；不要叠加第二个修复掩盖第一个问题。
- 结束前查看 `git status` 与 `git diff`，隔离无关改动但不擅自回滚他人内容。按影响面检查兼容、性能、日志、维护和回退风险，先交 `code-review`，再交 `memory-put` 询问归档。
