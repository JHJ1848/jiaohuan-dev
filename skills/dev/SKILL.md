# 开发(Dev)

遵从 `../../rules/engineering-principles.md`；只执行已确认的范围。实施前必须读 `references/implementation-and-verification.md`。

- 新增功能先完成“新增功能审视卡”：先读相关业务流程记忆，再检查当前模块的代码约定、实现流程、复用方法、最小改动边界和留痕方案；记忆只提供业务意图，不替代代码证据。审视结果未形成或出现新疑点时，停止实施并回到 `debug` 或探索(Explore)。
- 核对目标、不变量、历史约束、影响范围和验收。语义、数据范围或风险出现新疑点时停止并回到 `debug` 或探索(Explore)。
- 只做最小、可逆改动；不顺手重构、不加未经证实的回退(fallback)、默认值或吞错。新增状态码、阈值、模式串和错误码等字面量先查找并复用已有命名常量；确属外部契约时，在边界集中命名并注明来源，禁止散落魔法值(Magic Value)。
- 方法规模以现有仓库风格为准，通常控制在 50~200 行；不得为达到下限扩写。超过 200 行，或分支、外部调用、事务/并发和副作用明显集中时，先说明最小拆分边界、影响面和回退点，获确认后再封装步骤；复杂步骤补充解释原因的简洁注释。
- 关键节点建立日志链：入口、关键分支、外部调用/持久化前后、拒绝出口和异常结果均按 `[模块功能]` 记录必要状态与任务/请求标识；不记录令牌、密码、Cookie 或大对象。缺少安全标识时明确记录不可追踪原因。
- 主任务把已证实实施结果更新到 `path.json` 和临时证据；复杂或高风险改动明确交由用户实测。
- 按“基线复现 -> 单一原因最小修改 -> 精确验证 -> 读取 diff/日志证据 -> 决定下一轮”的修改-验证循环执行；用户未授权时不擅自发送真实请求。已授权时使用最小 Bash 请求和环境变量令牌，写入与读取分开并断言目标字段；失败或出现新行为立即回到 `debug`。
- 交接时明确报告：新增魔法值及处理、方法规模/拆分变化、关键日志覆盖、验证命令与证据边界。完成实施变更后先交 `code-review`，再交 `memory-put`，不自动归档。
