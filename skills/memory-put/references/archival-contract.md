# 归档合同

## 临时证据与协作

- 工作期间把事实、决策、候选和排查历史写入 `.agents/project-memory/temp/<task>/`；主任务维护 `task.json` 与 `path.json`，子智能体(Agent)只能写 `children/<agent>/` 草稿。
- `path.json` 是轻量子上下文，不是持久状态机(State Machine)：节点摘要 5-20 字，状态限于已证实、已排除、待确认、已实施，并附受管证据与短结论。
- 任务完成后主动询问是否归档。用户确认或明确要求后才执行 `put`；未确认时保留临时材料，不自动写正式文档。

## 价值评估

评估而非“价值门禁”。命中任一项通常值得归档：核心规则/接口/数据/安全/事务/部署改变；根因或取舍复杂；跨边界或影响范围大；同类问题高复发且易误判。低价值的格式、拼写和显而易见单点修复应说明跳过。

## 正式记录与三层架构

- 严格执行三层记忆归档规范：
  - **第一层（主记忆与工程约束）**：`AGENTS.md` 存储工程规范与代码环境；`MEMORY.md` 存储业务底层不变量、全局专题索引与全局变更索引。
  - **第二层（专题受控记忆）**：`docs/memory/<专题>.md` 仅维护长期架构设计、业务契约、领域事实以及对应专题的变更索引与简述；严禁堆砌具体代码改动的流水账。
  - **第三层（专题改动明细）**：所有具体工程实施与排查改动必须写入对应专题目录 `docs/change/<专题>/YYYY-MM-DD_中文简述.md`。
- 改动明细文档统一采用**四段式**结构（历史五段/六段保持只读兼容）：
  1. `## 一、问题/需求`：只写现象、目标和范围，控制在几句话内；
  2. `## 二、原因分析`：只写已确认原因、关键证据和排除结论；无证据标记为“待确认”，严禁将推测写成事实；
  3. `## 三、测试结果`：记录验证方式与结果（Exit Code、界面断言等）；未测试明确写“未测试”；
  4. `## 四、备注`：记录风险、TODO、回退方式、关联专题或补充信息。
- **反空话废话与极简精炼写入硬约束 (红线)**：
  - 归档文档必须使用精炼简洁的话语精准写入，严禁长篇大论和泛泛而谈，严禁说空话和废话；
  - 避免无实际作用的修饰语，优先写问题、原因、结果和必要备注；
  - 要求一眼就能找到重心，强制以客观事实、量化指标、确切接口/字段与代码物理位置精准呈现。
- 先按同义词、旧接口名、入口、关键状态和目标查同类记录。相同场景合并；同标题摘要变化时，运行时先拒绝覆盖，核对历史后以 `put --replace --change-record docs/change/<专题>/<记录>.md` 明确替换，或标记 `superseded` 并关联替代记录；重要历史变化写入 `docs/change/<专题>/`，不在主索引或专题受控记忆重复堆正文。
- 变更记录可在用户明确要求且确有发布、回退或审计价值时附少量相关 `.java`、`.vue`、`.ts` 等源码快照或精确路径；先扫描秘密，保留原始相对路径与用途，不复制整仓或无关代码。
- 正式写入前扫描标题、字段和全部受管草稿。命中秘密即拒绝，要求人工脱敏；不能自动替换或回显秘密。

## 保留与输出

受管临时材料保留七天；七天至三十天按 ISO 自然周归入 ZIP；最多保留七个周桶。未知文件、链接、不完整归档和清理失败一律保留并报告。

归档结果末尾列出实际主记忆、专题、功能、变更文档与替代关系；无正式写入则写“记忆引用：无”。
