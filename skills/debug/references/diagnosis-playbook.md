# 诊断执行要点

## 场景-目标卡

开始时只记录已知事实：场景（入口、角色、数据、状态）、目标与不变量、差距（现象/错误）、验收（请求、日志、查询或用户操作）。存在会改变业务行为的多个解释时，先请用户选择。

## 影响分流

- L1：稳定复现且明确单点，不改变业务语义或对外约定；仍先核对证据后交 `dev`。
- L2：单一职责内的业务规则偏差；补齐生命周期、输入、规则和状态。
- L3：跨模块、消费者、数据、事务或外部服务；先明确边界、所有者、前后置条件和回退范围。
- L4：广泛不可用、数据/安全风险或不可逆影响；先止损、隔离、恢复或回退并保留现场，风险受控后再诊断。紧急动作仍需用户授权，除非已有项目事故预案明确授权。

这是复杂度分流，不是持久状态机(State Machine)。

## 证据循环(Loop)

1. 先按“外部环境 -> 数据 -> 现有代码”取得最小事实；修改前查看 Git、`docs/change/`、记忆、接口契约和替代路径，推断但不臆造历史意图。
2. 给出一个可证伪假设：它必须同时解释现象和不变量。会话中可说明当前假设、暂定置信度与证据；`path.json` 只保存短摘要、状态、证据引用和结论。
3. 用最小查询、日志、请求、数据库或调用链验证。用户的推测不是事实，尤其不能据此前端推测直接添加后端条件。
4. 证实后形成最小计划；排除后记录原因并提出下一个假设。连续三次独立假设被排除、长期无进展或需要业务取舍时，停止尝试修改，汇总已排除路径并请求用户决定。

## 计划与接口证据

- 计划必须写清根因证据、改动位置、不变量、影响面、验证方法、回退条件和未知项；对业务含义或高风险写入先进行必要的多轮确认。
- 真实 HTTP 复现仅在用户授权目标环境后执行。请求体放临时文件，认证头用环境变量；保留 URL、方法、非敏感头、状态和断言，不保存凭据或完整敏感响应。
- 令牌通常由用户提供为环境变量；用户明确授权长期登录接口与凭据时，可在任务级临时命令中换取令牌后立即调用 `http-check.sh`。不把登录流程、凭据或令牌写入 Skill、记忆、脚本参数或通用 HTTP 平台。
- 写后读异常先分别证明写入响应、关联数据、独立读取和列表映射；不得在无证据时同时重写写入端与读取端。

## 诊断交接

交给 `dev` 前输出：已证实根因、已排除路径、最小改动、不可变业务规则、验证步骤、风险与用户待确认事项。没有根因时明确停止条件和下一条最小证据动作。
